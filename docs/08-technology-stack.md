## 10.2 Backend choice — justification (the "choose best option")

**Recommendation: NestJS (standalone API) over Next.js API routes.**

Reasons:
- **Domain complexity:** many bounded modules (members, billing, payroll, workouts…). NestJS modules/providers/guards map cleanly to this; RBAC + branch-scoping implemented once as guards/interceptors.
- **Background work:** payroll runs, recurring expenses, scheduled notifications, report generation, webhook processing — best handled by a dedicated Node service with BullMQ workers, not serverless request handlers.
- **Separation of concerns:** the mobile-first PWA and any future native app share one clean REST API; Next.js focuses on rendering.
- **Testability & long-running connections:** easier DB pooling, cron, and websockets (chat P2) in a persistent server.

**Alternative (smaller team / faster MVP):** keep everything in **Next.js Route Handlers + server actions** and move heavy/async jobs to a small worker later. Acceptable for MVP; migrate hot paths to NestJS as scale grows. The API contract in `07-api-documentation.md` is identical either way.

## 10.3 Auth choice — Clerk vs Auth.js

- **Clerk (recommended for speed):** hosted OTP/SMS, sessions, MFA, prebuilt components; we map Clerk user → our `users.auth_provider_id` and attach role/branch claims. Fastest to production.
- **Auth.js (recommended for full control / cost):** self-hosted, no per-MAU cost, but we build OTP, MFA, and session hardening ourselves.

Either way: **authorization (roles + branch scope) lives in our backend**, never delegated to the auth provider. JWT carries `userId`, `role`, `branchIds`.

## 10.4 Key architectural decisions (ADRs, condensed)

1. **Money as integer minor units** everywhere; format at the edge.
2. **Branch scope enforced server-side** via a guard that injects an allowed-branch filter into every query.
3. **Idempotent payments/onboarding** with `Idempotency-Key` + gateway webhook reconciliation as source of truth.
4. **PWA** via `next-pwa`/Workbox: offline shell, cached exercise media, queued check-in/workout logs.
5. **Reports** computed via SQL views/materialized views + cached; exports generated by workers.
6. **Feature flags** in `businesses.settings` (e.g., enable WhatsApp, multi-branch visiting default).
